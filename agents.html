Agent developers

Know which emails came from your people, and which came from their agents.

Signet7 puts a cryptographic seal on email. It does not encrypt the message. The seal binds the exact wording to a signing key. Before an agent pays, rebooks, or changes a bank account, it can ask Signet7 whether the instructions still match that seal and whether the sender is listed for your organization.

Why it matters

Agents act without a human gut check.

An inbox agent can draft replies, queue payments, and follow “urgent” instructions faster than a person can reread the thread. That is exactly where spoofed mail hurts: fake invoices, forged wire requests, and prompt-injection text that pretends to be the CEO. A seal does not stop every attack, but it gives the agent a machine-readable fact: these bytes were signed by a listed key, or they were not. Your integration must refuse when the verdict is not good enough.

Spoofed instructions

Prompt injection and look-alike domains land in the same inbox as real mail. Checking the seal first keeps the agent from treating unsigned wording as authority.

Scenario

Inbox agent refuses an unsealed wire request.

  1. Finance runs an inbox agent with permission to queue wires from email.
  2. Mail arrives: subject “URGENT wire transfer today,” body names a new account and amount. There is no Signet7 seal on the message file.
  3. The agent saves the original .eml and calls verify (MCP or API). The verdict is unsealed (or unknown if the check errored).
  4. Policy: no seal, no wire. The agent refuses, surfaces the thread to a human, and does not pass the instruction to the payment system.
  5. If the same wording later arrives sealed and listed from a known treasury address, verify returns sealed; the agent may still require human approval — Signet7 proves wording and listing, not business wisdom.

Signet7 does not move money. It returns evidence. The agent — your code — enforces the decision.
