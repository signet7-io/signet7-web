Put the gate where the action is proposed.

Signet7 does not require a replacement mailbox, traditional secure-email gateway, or endpoint agent for the supported pattern. Connect the decision interface to the agent or workflow that proposes the action, then enforce the returned result in the caller.

HTTP decision API

A structured policy decision for application code.

The current endpoint accepts explicit instruction and action fields. It returns structured content including the normalized action, authentication state, policy verdict, and allow/block result.

InputsAgent ID, message ID, claimed sender, body, exact action, tenant/auth context, optional signature and key.
ResultDerived trust state, canonical action, policy verdict, allowed boolean, and evidence identifier.
PrivacyThe persisted decision record uses protected identifiers and a request fingerprint rather than storing raw body, signature, or key verbatim.
LimitThe caller must perform the downstream authorization and execution control.

MCP integration

Expose the same bounded gate to agent harnesses.

The current MCP server publishes a verify_email_authenticity tool that derives the decision from the same core path. The name reflects its origin; the action field is what binds the proposed operation.

Technical pattern, not partnership

MCP materials demonstrate a protocol integration. They do not establish a certified agent-framework integration, vendor endorsement, marketplace listing, or hosted service.

What “no infrastructure” must not mean

Lower integration burden is not zero integration.

No replacement mailbox

Signet7 can sit beside existing email systems; it is not a mailbox provider.

No traditional SEG

The product is not positioned as an inbound spam, malware, or attachment-scanning gateway.

No endpoint agent

The supported pattern does not require a new endpoint-monitoring agent. An operated Signet7 service, credentials, policy, network path, and caller integration are still required.

Evaluation sequence

Integrate in a synthetic environment before consequential reliance.

1. Map the action

Define the exact canonical action and the caller that can enforce allow/block.

2. Map the trust input

Define sender/key enrollment, custody, revocation, and the supported signed instruction profile.

3. Exercise failure

Test missing signatures, self-signed keys, substituted actions, unknown identifiers, service unavailability, and caller bypass attempts.
